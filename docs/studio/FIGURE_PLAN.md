# The FigurePlan

`sprezzature_figures.core.figure_plan.FigurePlan` is the single source of
truth for a figure under construction. Neither the chat transcript nor the
rendered PNG is authoritative: only this Pydantic model is. Every accepted
chat edit produces a new `FigurePlan` (recorded as an
[`IterationRecord`](ARCHITECTURE.md#where-a-render-actually-lives)); Ralph
never edits the rendered image directly.

## Shape

```python
class FigurePlan(BaseModel):
    version: int = 1
    figure_kind: str                          # e.g. "bar", "connected-scatter"
    intent: UserIntent                        # what the user is trying to show
    bindings: dict[str, ColumnBinding]         # role name -> bound column(s)
    transformations: list[Transform]           # filter/sort/aggregate/... (see below)
    title: str
    subtitle: str | None
    source_note: str | None
    annotations: list[Annotation]
    style: StyleOptions                       # theme, width/height, font_scale, legend, ...
    output: OutputOptions                     # export format/dimensions
```

`UserIntent` (in the same module) is deliberately the same type the plan's
own spec calls `IntentAnalysis` in the LLM-schemas section: one shape, not
two names for the same fields.

## Bindings

`plan.bindings` maps a **role name** (e.g. `"region"`, `"value"`,
`"group_a"`) to the dataset column(s) feeding it. Role names aren't
arbitrary: for every `status="stable"` figure, the registry's
`required_roles`/`optional_roles` (`sprezzature_figures/catalog/
figures.json`, generated by `tools/build_figures_catalog.py`'s
`HAND_ROLES`) are named to match that generator's `DEMO_DATA` field names
exactly. That's what lets `_resolve_data()` in `studio/pages/editor.py`
turn a plan's bindings straight into `make_figure()`-ready rows with no
extra per-kind glue code:

```python
resolved = [{role: row[binding.column] for role, binding in plan.bindings.items()} for row in data]
```

## Transformations

`plan.transformations` is a list of `Transform`, a discriminated union
(`core.operations.Transform`) covering exactly plan §4.3's supported set:
`filter_value`, `filter_range`, `filter_temporal`, `sort`, `aggregate`,
`rename_display`, `top_n`, `group_others`, `calculate` (difference/ratio).
No free-form formulas.

These transformations are executed, not merely recorded.
`core.transformations.apply_transformations(rows, transforms)` runs each
step deterministically, in list order, over `list[dict]` rows: one closed
applier per transform type, no code evaluation. `_resolve_data()` in
`studio/pages/editor.py` calls it on the imported rows (keyed by the
original column names) before mapping columns onto role names, so a filter
or sort requested in the chat actually changes the rendered figure. The
export bundle applies the same step, so `data/transformed.csv` in a
`.sprezzature.zip` is the data the figure is really built from. Two rules
keep the output trustworthy: a transform whose column is absent from every
row is skipped with a note rather than silently emptying the figure, and
rows are never mutated in place. `rename_display` is deliberately a data
no-op, since the render contract keys data by role and a display rename is
a labelling concern for the style layer.

## Operations vs. transformations

Don't confuse `Transform` (a data-shaping step, lives inside
`FigurePlan.transformations`) with `FigureOperation` (a chat-driven *edit
to the plan itself*: `SetTitle`, `BindColumn`, `AddFilter`, ...). An
`AddFilter` operation *carries* a `Transform` as its payload; applying that
operation is what appends the transform to the plan. See
[RALPH_LOOP.md](RALPH_LOOP.md) for the full operation list and which ones
Ralph can apply on its own vs. which need your confirmation.
